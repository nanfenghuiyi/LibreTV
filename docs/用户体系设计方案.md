# LibreTV 用户体系设计方案（Cloudflare Workers + D1）

> 基于 main 分支（Next.js 15 重构版 v2.12.3）现状分析，目标平台为 Cloudflare Workers（OpenNext 部署，`wrangler.jsonc` 已含 D1 绑定）。

## 一、现状分析

### 1.1 当前鉴权与数据架构

| 维度 | 现状 | 关键代码 |
|------|------|----------|
| 鉴权模型 | **单一共享密码**：`PASSWORD` 环境变量，所有访客输同一密码，登录后身份完全相同 | `src/lib/auth.ts`、`src/app/api/auth/route.ts` |
| 会话 | 无状态 HMAC 签名 cookie：`<expiresAt>.<hmac>`，90 天有效，签名密钥取 `PROXY_SECRET`（未配置则从 `PASSWORD` 派生） | `auth.ts` 的 `signSession()/verifySession()` |
| 守卫 | `guardRequest()` 统一拦截 API 路由，未登录 401（含每分片都走的 `/api/proxy`） | `src/lib/api-guard.ts` |
| 管理员 | 与普通登录者无区别：凭同一密码编辑站点共享源 | `/api/shared/sources`、`/api/publish` |
| 用户数据 | **全部存浏览器本地**：IndexedDB（观看历史/播放进度/搜索历史/测活缓存）+ localStorage（设置快照） | `src/lib/db.ts`（Dexie）、`src/lib/store.ts`（zustand persist） |
| 服务端存储 | D1 仅一张 `shared_config` 单行 KV 表（自动建表），存站点级共享源 | `src/lib/shared-config.ts`、`d1-seed.sql` |
| 限流 | 登录限流为内存 Map，Workers 多隔离实例间不共享（尽力而为） | `auth.ts` 的 `checkRateLimit()` |

### 1.2 现状痛点（用户体系要解决的问题）

1. **换设备/清缓存即丢数据**：观看历史、进度、收藏、源配置全在浏览器本地，无法跨设备同步。
2. **无个人身份**：多人共用站点时无法区分「谁在看什么」，任何登录者都能改共享源（管理员能力无分级）。
3. **密码不可改**：改密码只能改环境变量并重新部署，且会立即使所有会话失效。
4. **无法管控注册**：密码一旦泄露即完全失控，无账号粒度的封禁/回收手段。

### 1.3 Cloudflare 平台约束（方案设计的前提）

| 约束 | 影响 |
|------|------|
| 免费版 CPU 时间 10ms/请求 | **密码哈希算法必须控制迭代次数**（详见 4.2） |
| 无长驻内存 | 内存限流/缓存退化为「每实例独立」，登录限流只能尽力而为 |
| 热路径 `guardRequest` 每个 HLS 分片请求都会执行 | 会话校验必须保持**无 D1 读**，否则视频播放每分片 +1 次 DB 读 |
| D1 免费额度：5GB 存储 / 500 万行读/天 / 10 万行写/天 | 用户体系为低频写负载，额度充裕 |
| `nodejs_compat` 已启用 | `node:crypto`（HMAC、timingSafeEqual）可用；**scrypt 不受支持** |
| Docker/Node 部署无 D1 | 用户体系必须能整体降级，回退现有单密码模式 |

## 二、目标与非目标

### 目标

1. **多用户账号**：用户名 + 密码注册/登录，每账号独立身份与角色。
2. **数据云端同步**：观看历史、播放进度、搜索历史、设置快照跨设备同步，离线仍可用（IndexedDB 保留为本地层）。
3. **角色分级**：`admin`（管理用户/邀请码/共享源）与 `user`（仅个人数据）。
4. **注册管控**：默认邀请码制，管理员在站内生成邀请码。
5. **完全向后兼容**：现有 `PASSWORD` 部署升级后零迁移成本；无 D1 环境（Docker）自动降级为现有单密码模式。

### 非目标（后续可扩展，本期不做）

- 第三方 OAuth 登录（GitHub/Google：国内可用性问题，且需应用注册）
- 邮箱注册/找回密码（需接入邮件服务如 Resend）
- 多因素认证
- 用户间数据分享/社交功能

## 三、总体架构

```
浏览器
 ├─ IndexedDB / localStorage（本地层，保留现状，离线可用）
 │    ▲ 拉取合并 / 防抖推送
 │    │
 ├─ /api/auth/*        注册、登录、会话查询、改密
 ├─ /api/user/data/*   个人数据同步（历史/进度/设置）
 └─ /api/admin/*       用户管理、邀请码（仅 admin）
        │
 Cloudflare Worker（OpenNext）
  ├─ 会话：无状态 HMAC token（扩展为携带 userId，校验零 DB 读）
  ├─ 账号/数据：D1（users、invites、user_data 三张表，自动建表）
  └─ 守卫：resolveAuth() 替代 guardRequest()，返回 {userId, role}
```

**选型说明**——为什么不用其他方案：

| 备选 | 结论 |
|------|------|
| Cloudflare Access（Zero Trust SSO） | 面向企业内网场景，免费版 50 席位，需全员接入 CF 身份源，访客体验差，不符合「公开影视站」定位 |
| 第三方 Auth 服务（Auth0/Clerk/Auth.js + OAuth） | 引入外部依赖与免费额度风险；国内访问 Google 受阻；项目当前风格是零外部依赖，不引入 |
| Workers KV 存用户数据 | KV 最终一致 + 免费版写额度 1000 次/天，用户数据高频写（进度每几秒一次）不合适；D1 无此问题 |
| Durable Objects 存会话 | 免费版 DO 仅支持 SQLite 后置类且引入复杂度；无状态 token 已够用 |
| **D1 + 无状态签名会话（本方案）** | 复用现有 D1 绑定与「自动建表 + 降级」模式，改动最小，热路径零 DB 读 |

## 四、认证与会话设计

### 4.1 账号模型与 D1 表结构

沿用 `shared_config.ts` 的「首次写入自动建表 + 无 D1 降级」模式，新增三张表（不新增 wrangler binding，复用 `DB`）：

```sql
-- 用户表
CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,          -- uuid（crypto.randomUUID()）
  username      TEXT NOT NULL UNIQUE,      -- 2~32 位，[a-zA-Z0-9_-]
  password_hash TEXT NOT NULL,             -- pbkdf2$<iterations>$<salt_b64>$<hash_b64>
  role          TEXT NOT NULL DEFAULT 'user',   -- 'admin' | 'user'
  disabled      INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  last_login_at INTEGER
);

-- 邀请码表（注册管控）
CREATE TABLE IF NOT EXISTS invite_codes (
  code       TEXT PRIMARY KEY,             -- 8~16 位随机串
  created_by TEXT NOT NULL,                -- 生成者 user_id
  used_by    TEXT,                         -- 使用者 user_id（一次性）
  used_at    INTEGER,
  expires_at INTEGER NOT NULL,
  created_at INTEGER NOT NULL
);

-- 用户数据表（通用 KV：type + key 两级，单表覆盖所有同步数据）
CREATE TABLE IF NOT EXISTS user_data (
  user_id    TEXT NOT NULL,
  type       TEXT NOT NULL,                -- 'history' | 'progress' | 'search_history' | 'settings'
  k          TEXT NOT NULL,                -- 与客户端现有主键一致（如 `${sourceKey}_${vodId}`）
  v          TEXT NOT NULL,                -- JSON
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, type, k)
);
```

**内置管理员**：用 `PASSWORD` 登录（不带用户名）时，自动创建/匹配内置账号 `admin`（role=admin）。这样：

- 现有部署升级后，管理员**无需任何迁移**，老密码即管理员身份；
- `PASSWORD` 成为「管理员主密码」，始终可登录（应急后门，用于找回 admin 权限）；
- `getSecret()` 现有派生逻辑不变，`PASSWORD` 未设置时整个用户体系不可用（与现状 503 一致）。

### 4.2 密码哈希（10ms CPU 约束下的取舍）

Workers 免费版每请求 10ms CPU。PBKDF2 用 WebCrypto 原生实现（`crypto.subtle.deriveBits`），比 JS 实现快一个量级，但迭代次数仍需保守：

- **算法**：PBKDF2-SHA256，**25,000 次迭代**，16 字节随机盐，输出 32 字节
- **存储格式**：`pbkdf2$25000$<salt_b64>$<hash_b64>`（参数内嵌，未来可平滑升级算法/轮数）
- **可选 pepper**：哈希前先 `HMAC(密码, PROXY_SECRET)`，即使 D1 泄露也无法离线爆破（pepper 不在库里）
- **验证方法**：`npm run preview` 后在登录接口打 `performance.now()` 日志，通过 `wrangler.jsonc` 的 observability 观察 CPU 时间；若超限可降至 15,000（注册默认强密码 + 登录限流 + 邀请码制补偿）
- 登录为低频操作（90 天会话），单次 ~10ms 可接受；**付费版 Workers（$5/月，30s CPU）则可提到 100k+ 迭代**
- 比较一律走 `crypto.timingSafeEqual`（沿用现有写法）

> 注：`node:crypto` 的 `scryptSync` 在 workerd 不受支持，不要使用；`pbkdf2Sync` 虽可用但 WebCrypto 版本为原生加速，优先后者。

### 4.3 会话 token 扩展（保持无状态、零 DB 读）

现有 token：`<expiresAt>.<hmac>`。扩展为：

```
token = base64url(<userId>).<expiresAtMs>.<hmac>
签名密钥 = HMAC(globalSecret, userId + ":" + password_hash 前 16 字符)
```

- **无状态**：`verifySession` 仅做 HMAC 校验 + 过期检查，热路径（`/api/proxy` 每分片）**零 D1 读**，与现状一致
- **改密即全端下线**：密码变更 → `password_hash` 变 → 该用户签名密钥变 → 旧 token 全部失效（无需会话表）
- **管理员主密码登录**：userId 固定为 `admin`（或内置用户行 id）
- **兼容策略**：旧格式 token（无 userId 段）视为 `admin` 身份继续有效至自然过期——升级瞬间所有已登录用户不掉线；如不接受可将旧 token 直接判无效强制重登（二选一，默认前者）
- **已知限制**（接受并记录）：管理员「禁用用户」后，该用户**已签发的 token 仍有效至过期**；缓解：`/api/user/data`、`/api/admin/*` 等敏感接口在 resolveAuth 时额外查一次 D1 校验 `disabled`（低频路径可承受），分片代理等高频路径不查。全局紧急踢人可通过轮换 `PROXY_SECRET` 实现

### 4.4 登录/注册接口行为

| 场景 | 入口 | 行为 |
|------|------|------|
| 主密码登录 | `POST /api/auth` `{password}` | 校验 `PASSWORD`，内置 admin 身份（现状行为的超集，UI 不变） |
| 用户登录 | `POST /api/auth` `{username, password}` | 查 users 表校验；返回含 role 的会话 |
| 注册 | `POST /api/auth/register` `{username, password, inviteCode?}` | 模式由 `USER_REGISTRATION` 环境变量控制：`invite`（默认）/ `open` / `off` |
| 会话查询 | `GET /api/auth/me` | 返回 `{verified, userId, username, role, userSystemAvailable}` |
| 改密 | `PUT /api/user/password` `{oldPassword, newPassword}` | 校验旧密码 → 更新 hash → 旧会话全失效 |

登录/注册沿用现有内存限流（`checkRateLimit`），并对注册增加每 IP 窗口计数（同实现）。可选加固：接入 **Cloudflare Turnstile**（免费）作为注册验证码，本期列为可选项。

## 五、用户数据同步设计

### 5.1 同步范围与职责划分

| 数据 | 客户端现状 | type | 同步策略 |
|------|-----------|------|----------|
| 观看历史 | Dexie `history` 表，上限 100 条 | `history` | 逐条 LWW（按 `timestamp`），云端拉取合并进 IndexedDB |
| 播放进度 | Dexie `progress` 表 | `progress` | LWW（按 `updatedAt`）；同键取 `position` 较大者兜底防回退 |
| 搜索历史 | Dexie `searchHistory` 表，上限 10 条 | `search_history` | 整体单键（`k='list'`）覆盖写，低价值数据从简 |
| 设置快照 | zustand persist `libretv-settings` | `settings` | 整体单键（`k='snapshot'`）覆盖写 + `updatedAt` LWW |
| 直播测活缓存 | Dexie `liveProbe` 表 | **不同步** | 设备本地性能缓存，体积大、时效短，无跨端价值 |

**分层原则**：IndexedDB/localStorage 仍是运行时唯一读写层（首屏零等待、离线可用）；云端是「异步镜像」，登录后合并一次，此后写入防抖推送。登出后本地数据保留，可手动清除。

### 5.2 同步 API

```
GET  /api/user/data?type=history|progress|search_history|settings
     → { rows: [{k, v, updatedAt}] }                    全量拉取（数据量小，不做分页）

PUT  /api/user/data
     body { rows: [{type, k, v, updatedAt}] }           批量 upsert（≤200 行 / ≤256KB）
     → 服务端拒绝 updatedAt 早于库内的行（幂等，乱序到达无害）

DELETE /api/user/data?type=history&k=<key>              单条删除（历史面板的删除按钮）
DELETE /api/user/data?type=history&all=1                清空某类（设置页「清空云端历史」）
```

安全上限：每用户 `user_data` 总行数软上限（如 500），PUT 时校验并在超限时拒绝并提示（防滥用写爆 D1）。

### 5.3 客户端同步流程

新增 `src/lib/user-sync.ts`（纯函数拆出便于 vitest 测试）：

```
登录成功
  → GET 全量拉取四类数据
  → 合并进本地（Dexie upsert + zustand setState）：
      history：按条目 timestamp 新者胜，合并后保留 MAX_HISTORY 上限
      progress：updatedAt 新者胜，同键 position 取大者
      settings：云端 updatedAt 更新才覆盖（本地刚改过的设置不被旧快照冲掉）
运行期间
  → upsertHistory / 进度节写 / 设置变更处挂防抖队列（3s 合并推送 PUT）
登出
  → 停止推送队列，本地数据保留（现状行为不变）
```

多设备并发以 `updatedAt`（客户端时钟）做 LWW；时钟偏差极端情况表现为个别条目旧值覆盖，属可接受代价，文档记录不做服务器时钟仲裁。

## 六、API 守卫与权限改造

### 6.1 `api-guard.ts` 演进

```ts
// 现状：guardRequest(req) → NextResponse | null（只回答「登没登」）
// 目标：resolveAuth(req) → { userId, role, legacy } | null
//   - legacy=true 表示主密码登录的内置 admin
//   - guardRequest() 保留为薄封装：resolveAuth 为 null 时返回 401，现有 15 个路由调用点零改动
//   - 新增 requireAdmin(res)：role !== 'admin' 时返回 403
```

各路由的权限归属：

| 路由 | 现状 | 目标 |
|------|------|------|
| `/api/search`、`/api/detail`、`/api/douban` 等内容类 | 登录即可 | 登录即可（任意角色） |
| `/api/proxy/[url]`、`/api/live/stream` | 登录即可 | 登录即可（高频，不查 D1） |
| `/api/shared/sources`（写）、`/api/publish` | 登录即可 | **仅 admin** |
| `/api/user/data`、`/api/user/password` | 无 | 登录即可（仅本人数据） |
| `/api/admin/*` | 无 | 仅 admin + 敏感操作查库校验 `disabled` |

## 八、兼容与降级策略

| 环境 | 行为 |
|------|------|
| Cloudflare Workers + D1（主路径） | 完整用户体系 |

## 十、安全清单

- 密码：PBKDF2（参数内嵌可升级）+ pepper + `timingSafeEqual`；最短 8 位；注册限流
- 会话：HttpOnly + SameSite=Lax + Secure（沿用现有推导）；改密全端失效；90 天过期
- 枚举防护：登录「用户不存在」与「密码错误」统一返回「用户名或密码错误」
- SQL：全部走 D1 `prepare().bind()` 参数化（现有代码已如此）
- 输入：用户名白名单字符 + 长度限制；PUT body 体积/行数上限；JSON schema 校验
- 管理面：admin 路由双重校验（token role + 库内 `disabled/role` 复查）
- 滥用防护：账号数上限、每用户存储上限、注册默认邀请码制；可选 Turnstile
